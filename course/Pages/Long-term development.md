## What 

In this semester, you will work on a project that already runs for a while, or you will start with a project with the aim of running for a longer time. In both cases, you'll need to keep thinking future-oriented to make the project successful in the long run. Three phases can be identified throughout the semester: Explore, Add Value, and Handover. 

![[analyze-realize-validate.png]]

## Why 

Working on a long-term project requires a set of skills you probably haven't worked on before, but which are essential to be able to start working as a new team member in an existing project, and handover your project to a new team (member). 

## How

Explore: When starting with a brown field project, take your time to get familiar with what is already there. 

- Identify stakeholders needs & expectations 
- Discover the code, walk through the existing work with a knowledge owner (if possible) 
- Understand the functional and non-functional requirements 
- Understand what is already done 
- Create or set-up a (transferable) initial development environment 

Add Value: Once you have confidence that the Exploration phase has been completed, the next phase starts. Keep your customer involved and stay focused at handing over the project at all times! This is not something you should only focus on in the last sprint. Work Agile and make sure your product is ready for a release (handover) at the end of each sprint. 

- Per sprint: Define a clear sprint goal 
- Define activities to increase maintainability, understandability & testability 
- Understand the expected maturity of your project 
- Keep your knowledge owner in the loop 
- Involve your stakeholders.
- Make sure you can release your product at the end of each sprint. 

Handover: In case it is already known to whom you should transfer, you can make a handover appointment. However, in many cases this will not be known yet. You can take a look at the handover documentation as if you're the new team member or ask a complete outsider to take a look. Keep the following in mind: 

- No Personal Lock-In 
- Give good 'starting advice' for new groups 
- Quality is assured 
- Retrospect your initial goals 
- Version management is present and can be taken over by a new team 
- Issue management is present and can be taken over by a new team, each bug is described as issue and discussed with PO, and issues have been identified as appropriate to start on in exploration phase for new team 
- Management of future development (for example user stories in backlog) is present and can be taken over by a new team 
- Future improvements of the product are identified 
- Documentation: Documents are up-to-date. (architecture, project definition, future work). 
- Security: Static Security analysis has been performed. For example, no hard-code passwords in code 
- Readability: Static analyzers are used to ensure a coding style and readability. 
- Dependency Management: External tools and libraries are described and use explicit versioning. 
- Dependency Management: All tooling can be handed over. There are no accounts linked to old developers, or trial versions that can expire. 
- Environment: Documentation is present that describes step for step a local set-up for a developer, resulting in a working version of the project. 
- Environment: Datasets are available for development purpose (including description how to use them in the project) 
- Environment: Documentation is set up to install a production environment from scratch. Preferably: configuration-as-code 
- Delivery: Forked repository, has a separate delivery branch for intake 
- Delivery: Pull requests to delivery branch are created, and are reviewed together with the knowledge owner 
- Delivery: A final transfer meeting is planned with the product owner
